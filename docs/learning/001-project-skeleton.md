# 001: Phase 0 project skeleton

## 1. What changed and why

Phase 0 sets up the empty but working skeleton that every later feature will build on: a PostgreSQL database in Docker, a Spring Boot 4.1.1 backend whose schema Flyway manages, a React + TypeScript frontend, automated tests against a real database, and CI. There are no business features yet. What now works: `docker compose up -d` starts the database, the backend connects to it and applies migrations, the frontend page reports whether the backend is healthy, and `./mvnw verify` proves all of this automatically.

## 2. How it fits together

There are two flows worth tracing: what happens when the **backend starts**, and what happens when the **page loads**.

**Backend startup (`./mvnw spring-boot:run`)**

1. `VantageApplication.main` calls `SpringApplication.run`. Spring Boot starts reading configuration from `application.yml`.
2. `spring.config.import: optional:file:../.env[.properties]` tells Spring to also load the root `.env` file as a properties file. `spring-boot:run` runs with `backend/` as the working directory, so `../.env` is the repo root. That makes `POSTGRES_USER`, `POSTGRES_PASSWORD` and the other variables available as properties.
3. The `${...}` placeholders in `spring.datasource.*` resolve against those values. Spring Boot auto-configures a `DataSource`, a HikariCP connection pool pointed at `jdbc:postgresql://localhost:5432/vantage`.
4. Flyway's auto-configuration runs **before** JPA starts. It connects, creates the `flyway_schema_history` table if it's missing, finds `classpath:db/migration/V1__baseline.sql`, runs it, and records the result in that table. If V1 is already recorded (as on every start after the first), it does nothing.
5. Hibernate (JPA) starts with `ddl-auto: validate`. It compares entity classes to the schema. There are no entities yet, so there is nothing to check.
6. Tomcat starts on port 8080. Actuator exposes `/actuator/health` and nothing else.

**Page load (`http://localhost:5173`)**

1. The browser loads `index.html` from the Vite dev server, which loads `src/main.tsx`, which renders `<App />`.
2. `App` starts in state `{ kind: 'loading' }` and renders "Checking backend…".
3. Its `useEffect` calls `fetchHealth(signal)` in `src/health.ts`, which calls `fetch('/actuator/health')`, a **relative** URL on the Vite origin (port 5173).
4. The Vite dev server matches the `/actuator` prefix in `server.proxy` (`vite.config.ts`) and forwards the request to `http://localhost:8080/actuator/health`.
5. Spring Boot's `HealthEndpoint` asks every `HealthIndicator` for its status. `DataSourceHealthIndicator` (the `db` component) borrows a connection and runs a validation query. The overall status is the worst of all the components.
6. The JSON goes back through the proxy. `fetchHealth` checks that the response is JSON and returns it, and `App` moves to `{ kind: 'loaded', health }`. `HealthStatus` renders "Backend is UP" and one list item per component.
7. If the backend is down, the proxy answers 502 with a non-JSON body. `fetchHealth` throws, and the page shows the `role="alert"` error message.

## 3. Walkthrough, in reading order

**`docker-compose.yml`** defines one service, `postgres`, on the `postgres:18-alpine` image. The lines that matter:
- `environment` passes `${POSTGRES_DB}` and the other credentials. Docker Compose reads these from `.env` in the same directory automatically.
- `volumes: postgres-data:/var/lib/postgresql` is the named volume that keeps data across `docker compose down`/`up`. The mount point is PostgreSQL 18 specific (see section 7).
- `healthcheck` with `pg_isready` lets `docker compose up --wait` block until the database actually accepts connections. The `$$` escapes `$` so the container's shell expands the variable, not Compose.

**`.env.example` / `.gitignore`**: `.env.example` is the committed template. `.gitignore` ignores `.env` and `.env.*` but re-includes `.env.example` with `!`.

**`backend/pom.xml`** was generated by start.spring.io for Boot 4.1.1. Boot 4 split auto-configuration into per-technology modules, so the starters look different from older tutorials:
- `spring-boot-starter-webmvc` (Boot 3 called it `spring-boot-starter-web`).
- `spring-boot-starter-flyway`. In Boot 3 you added `flyway-core` directly and auto-configuration came along for free. In Boot 4, Flyway support without this starter means Flyway **silently never runs**.
- `flyway-database-postgresql` is Flyway's own PostgreSQL support module (Flyway 10+ needs it).
- Each main starter has a matching `-test` starter (`spring-boot-starter-webmvc-test`, and so on) that brings in the test slices and helpers for that module.
- `testcontainers-postgresql` and `testcontainers-junit-jupiter` use the Testcontainers 2.x artifact names (1.x called them `postgresql` and `junit-jupiter`).

**`backend/src/main/resources/application.yml`** is the most important config file:
- `spring.config.import` loads `.env`, as described above.
- `spring.datasource.*`: host, port and database name have defaults, but username and password do not, so a missing secret fails loudly instead of falling back to something guessable.
- `spring.jpa.hibernate.ddl-auto: validate` means Hibernate never alters the schema.
- `management.endpoints.web.exposure.include: health` and `show-components: always` expose only health, with per-component status but not details.

**`backend/src/main/resources/db/migration/V1__baseline.sql`** contains only comments. The file name is the contract: `V1` is the version, `__` separates it from the description, and `baseline` becomes the description Flyway stores.

**`backend/src/main/java/com/vantage/common/package-info.java`**: Java has no such thing as an empty package on disk that Git will keep, so a `package-info.java` holds the package and documents what belongs in it.

**`backend/src/test/java/com/vantage/TestcontainersConfiguration.java`**: a `@TestConfiguration` with one `@Bean` returning a `PostgreSQLContainer`. `@ServiceConnection` is the key annotation. Spring Boot starts the container, reads its random host port and credentials, and supplies them as the `DataSource` connection details, overriding `spring.datasource.*`. That's why tests need no `.env`.

**`backend/src/test/java/com/vantage/ApplicationIntegrationTest.java`**:
- `@SpringBootTest` starts the whole application context, including Flyway and JPA. `@Import(TestcontainersConfiguration.class)` swaps in the container database.
- `@AutoConfigureMockMvc` plus `MockMvcTester` sends requests through the full Spring MVC stack without opening a real network port. `MockMvcTester` is the AssertJ-style API that pairs with `assertThat`.
- `healthEndpointReportsUpIncludingDatabase` checks both `$.status` and `$.components.db.status`. The second check matters: it proves the database specifically is healthy, not just the app.
- `appliesBaselineMigrationOnStartup` uses the `Flyway` bean's `info().current()` API to assert that version `1`, `baseline`, is in state `SUCCESS`.
- The constructor has `@Autowired` so JUnit lets Spring supply the parameters (constructor injection, per CLAUDE.md).

**`backend/src/test/java/com/vantage/TestVantageApplication.java`** (generated): running its `main` starts the app locally against a Testcontainers database instead of compose. It's handy, but you don't need it.

**`frontend/vite.config.ts`**: the `server.proxy` entry plus the comment explaining why.

**`frontend/src/health.ts`**: the `HealthResponse` type and `fetchHealth`. Note the JSON check. Actuator returns **503 with a JSON body** when the app is DOWN, so "non-2xx means error" would be wrong here. A DOWN report is still a valid answer.

**`frontend/src/App.tsx`**:
- `HealthState` is a *discriminated union*: `kind` tells TypeScript which other fields exist. That makes invalid states such as "loading with an error message" impossible to represent.
- The `useEffect` with an `AbortController` cancels the request on unmount.
- `HealthStatus` switches on `state.kind`. TypeScript checks that every case is handled.

**`.github/workflows/ci.yml`**: three jobs. `changes` runs `dorny/paths-filter` and outputs `backend`/`frontend` flags. `backend` and `frontend` have `needs: changes` and an `if:` on those flags. `setup-java` with `cache: maven` and `setup-node` with `cache: npm` handle dependency caching.

**Skipped as boilerplate:** `mvnw`/`mvnw.cmd`/`.mvn/` (the Maven wrapper scripts, pinned to Maven 3.9.16), `VantageApplication.java`, the Vite template's `tsconfig*.json`, `eslint.config.js`, `main.tsx`, and the two sub-project `.gitignore` files.

## 4. Design decisions

| Decision | Alternative | Why this one |
|---|---|---|
| **Flyway owns the schema; `ddl-auto: validate`** (from the task spec, consistent with CLAUDE.md's migration rule) | `ddl-auto: update`, where Hibernate alters tables to match entities | `update` makes silent, unreviewed schema changes and can't do things like renames or data backfills. Versioned SQL files are reviewable and repeatable. **ADR-worthy.** |
| **Testcontainers against real PostgreSQL** (CLAUDE.md: "No H2") | In-memory H2 | H2 only approximates PostgreSQL. `NUMERIC`, `TIMESTAMPTZ`, JSON and SQL dialect differences would let tests pass while production breaks. |
| **Same image (`postgres:18-alpine`) in compose and tests** | `postgres:latest` (Initializr's default) in tests | Tests should match what you develop against. `latest` would silently jump major versions. |
| **One root `.env`, loaded by Spring via `spring.config.import`** | Export variables in your shell, or keep a separate `application-local.yml` | One file holds credentials for both compose and the backend. Real environment variables still win, so CI and deployment work the normal way. |
| **Vite dev proxy instead of CORS** (from the task spec) | `@CrossOrigin` or a global CORS config in Spring | Same-origin in development mirrors a production reverse-proxy setup. It also means there's no CORS policy to get wrong once auth cookies exist in Phase 2. **ADR-worthy** (it shapes how auth will work). |
| **`show-components: always`, not `show-details`** | `show-details: always` | Components are enough to see that the database is down. Details leak the database product and version and disk paths to anyone. |
| **`MockMvcTester` rather than a real HTTP port** | `@SpringBootTest(webEnvironment = RANDOM_PORT)` with an HTTP client | It's faster, and it's Boot 4's AssertJ-native testing API. Real-port testing becomes worth it once you're testing things like security filters over real HTTP, and even those work with MockMvc. |
| **`dorny/paths-filter` job** | Two separate workflow files, each with `on.paths` | The task asked for one workflow with two jobs. Workflow-level `paths` can only skip the whole workflow. |
| **ESLint in the frontend** | Oxlint (create-vite 9's new default) | ESLint is the widely used standard, and CLAUDE.md prefers conventional choices. |

A general stack ADR ("Spring Boot 4 + PostgreSQL + Flyway + Testcontainers") would also be a good first entry in `docs/adr/`.

## 5. Concepts to study

- **Auto-configuration**: Spring Boot creates beans (`DataSource`, `Flyway`, `HealthEndpoint`) based on what's on the classpath and which properties are set. That's why adding `spring-boot-starter-flyway` alone makes migrations run.
- **Externalized configuration and property placeholders**: `${POSTGRES_USER}` in `application.yml` resolves from environment variables and imported files, in a defined precedence order.
- **Database migrations (Flyway)**: versioned, immutable SQL files, plus a history table that records what has been applied.
- **Connection pooling (HikariCP)**: the `DataSource` keeps reusable connections open. The health check borrows one.
- **Testcontainers and `@ServiceConnection`**: throwaway real dependencies in Docker for tests, wired into Spring automatically.
- **Integration test vs unit test**: `ApplicationIntegrationTest` boots the whole context against a real database, where a unit test would test one class in isolation.
- **Same-origin policy and CORS**: why a browser blocks `localhost:5173` from reading `localhost:8080` responses, and how a proxy avoids the problem.
- **React `useEffect` cleanup and `AbortController`**: cancelling side effects when a component unmounts.
- **Discriminated unions in TypeScript**: `HealthState` modelling mutually exclusive UI states.
- **Docker named volumes**: storage that outlives the container.

## 6. Try it yourself

1. Stop the database (`docker compose stop`) while the backend is running, then reload the page. Predict the HTTP status and what the page shows before you look. Then check `curl -i localhost:8080/actuator/health`.
2. Add a `V2__example.sql` that creates a small table, and run `./mvnw verify`. Which assertion fails, and why? What would you change? (Delete V2 afterward. It's never been committed, so that's allowed.)
3. Change `postgres:18-alpine` to `postgres:17-alpine` **only** in `TestcontainersConfiguration`. Do the tests still pass? What could go wrong later if the versions drift?
4. Remove `spring-boot-starter-flyway` from `pom.xml` (keep `flyway-database-postgresql`) and run the tests. Read the failure closely: what does it tell you about how Boot 4 wires Flyway?

## 7. Review carefully

- **PostgreSQL 18 volume path.** Starting with version 18, the official image stores data in `/var/lib/postgresql/18/docker`, and mounting at the old `/var/lib/postgresql/data` path makes the container refuse to start. I mounted at `/var/lib/postgresql` and verified that data survives `docker compose down`/`up`. Keep this in mind if you follow older tutorials.
- **`../.env` depends on the working directory.** It works for `./mvnw spring-boot:run` because the plugin runs from `backend/`. If you run the app from an IDE with the repo root as the working directory, the import silently finds nothing (it's `optional:`). You'd then get a clear authentication failure, not a mystery.
- **Startup warning left in place:** `spring.jpa.open-in-view is enabled by default`. I didn't set it because it wasn't in the task. It should likely be `false` (see "Suggestions" in the task summary).
- **Generated test starters.** Initializr added `-test` starters for actuator, data-jpa, flyway and validation that nothing uses directly yet. They're harmless and conventional, but they're dependencies you didn't explicitly choose.
- **`TestVantageApplication.java`** is Initializr output that wasn't asked for. Keep it or delete it.
- **CI has not actually run**, because this directory isn't a Git repository yet. The workflow parses as valid YAML, but the first push is its real test.
- **Local verification details:** Java 21 came from `brew install openjdk@21` and isn't on your `PATH` yet. I ran the backend with `JAVA_HOME=/opt/homebrew/opt/openjdk@21`.

## 8. Check your understanding

1. Why does the test suite pass on a machine with no `.env` file?
2. What would happen on startup if someone set `ddl-auto: validate` but added an `@Entity` class without a matching migration?
3. Why does `fetchHealth` check the `content-type` header instead of `response.ok`?
4. If you edit `V1__baseline.sql` after it has been applied to your local database, what happens the next time the backend starts?
5. Why is the default for `POSTGRES_HOST` fine to commit, but not a default for `POSTGRES_PASSWORD`?

<details>
<summary>Answers</summary>

1. `@ServiceConnection` on the container bean supplies the connection details (URL, username, password) from the running Testcontainers database, overriding `spring.datasource.*`. The `.env` import is marked `optional:`, so its absence is fine.
2. Startup fails. Hibernate's schema validation finds the missing table or columns and throws, so the application never starts. That's the point: a mismatch is caught immediately instead of at the first query.
3. Actuator responds with **503 and a valid JSON body** when the app is DOWN. `response.ok` would treat that as a failure and hide the useful report. A non-JSON response, like the proxy's 502 when the backend isn't running, is the real "can't reach it" case.
4. Flyway compares a checksum of each applied migration with the file on disk. The checksum no longer matches, so validation fails and the app refuses to start. That's why committed migrations are never edited.
5. A host default like `localhost` reveals nothing and is correct for local development. A password default would put a credential in the repository, and a deployment that forgot to set the real one would silently run with a known password instead of failing.

</details>
